☷

Think of skills as recipes in a shared cookbook. Anyone on the team can write a new recipe or tweak an existing one. The chef (Claude) reads the cookbook and cooks what you ask. You don't need to know how the kitchen works — just write the recipe in plain Markdown.

Skill Inheritance

Skills follow a cascade model: Global → Team → Local. Like CSS inheritance or class hierarchy — the most specific definition wins.

△
The cascade: from foundation to surface
Imagine a building. The foundation (Global) provides base capabilities — calendar, research, AI generation. The walls (Team) add shared team workflows — CRM, lab management, content voice. The furniture (Local) customizes for the specific project — sprint monitoring, onboarding flows. Each layer inherits from the one below and can override it.
How Claude Code resolves a skill
When you type /AIM-crm, Claude Code searches in this order:
1. Project .claude/skills/AIM-crm
→
2. Symlink → aim-rules/skills/AIM-crm
→
3. Global ~/.claude/skills/AIM-crm
First match wins. If the project has a local AIM-crm, it overrides the team version. If the team vault has one (via symlink), it overrides global. This means any project can customize team skills without affecting others.
Example: AIM-crm lives at 3 levels
Team vault has the canonical /AIM-crm with partner tracking, offers, dashboard. The notes project has a symlink that points to it — so Claude reads the team version. But for a specific client project, you could create a local override with custom fields — and that project would use the local version while everything else keeps using the team one.
★ Same skill name, different behavior per context — without branching or versioning
⇄
Why this matters for the team
In Claude Code, skills are the DNA of behavior. CLAUDE.md sets the overall personality. Skills define specific capabilities. The inheritance model means the team can evolve shared skills collaboratively, while any individual context can diverge when needed — without merge conflicts, without coordination. It's convention over configuration for AI agents.

Skill Storage

Every skill is a folder with a SKILL.md file inside. That's it — Markdown with YAML frontmatter. No compilation, no build step, no binary.

☷ aim-rules/skills/AIM-pm/SKILL.md
1---
2name: AIM-pm
3description: Team Process Manager — review, sync, summary, track
4version: 2.1
5---
6

8
9Args: review | sync | summary | track <person>
10
11## When to use
12Weekly reviews, team syncs, tracking individual progress...
13
14## Instructions for Claude
151. Read team role cards from Org/HR/roles/
162. Pull Linear tasks for the relevant person
173. Cross-reference with Krisp meeting data...
☷
Markdown is the universal interface
Skills are not plugins, not packages, not APIs. They're plain text instructions that Claude reads and follows. The YAML frontmatter tells Claude what the skill is called and when to trigger it. The body tells Claude what to do. This means anyone who can write Markdown can write a skill — no programming required.

What YAML frontmatter controls
name — how you invoke it (/AIM-pm)
description — when Claude auto-triggers the skill
version — for tracking iterations

Claude reads all available skills at session start and matches them against your request. Description is the trigger — write it well.
What the body contains
Plain Markdown instructions: what to do, how to do it, which MCP servers to call, what format to output. Think of it as a detailed prompt template that Claude follows step by step. Can include code blocks, tables, decision trees — anything Markdown supports.

Symlink Bridge

Claude Code only discovers skills in two places. The team vault is neither. Symlinks are the bridge.

⚘
Two islands, one bridge
Claude Code sees ~/.claude/skills/ and .claude/skills/ in the working directory. The team vault (aim-rules/skills/) is on a different island — Claude can't see it directly. The symlink script builds a bridge: it creates filesystem links from the project's .claude/skills/ to each team skill folder. Claude follows the link and reads the team skill as if it were local.

Talk Blocks

Structured segments for the presentation with talking points and key messages.

1Stack Architecture

  • 3 layers: Global (personal) → Team (shared vault) → Local (project overrides)
  • Skills = Markdown files, not code. Anyone can edit in Obsidian
  • Symlinks bridge the vault to Claude Code discovery
  • Inheritance cascade: local overrides team, team overrides global
Key message: composable layer cake. Skills inherit like CSS — the most specific wins. Team edits propagate via Obsidian Sync. No deployment, no CI — just Markdown.

2Bot Infrastructure

  • Pulse — heartbeat, every 2h, 7 chats → AIM agi group
  • Claude bot — voice, interactive DM, full skill library
  • Allowlist access — only approved team members
  • Pulse gives ambient awareness, Claude bot gives direct AI access
Key message: bots are the nervous system. One pushes information automatically (pulse/heartbeat). The other responds to requests (voice). Together they make the stack accessible without a terminal.

3CTRL Dashboard

  • Single-file terminal dashboard, FastAPI backend (3500+ lines)
  • VOX AI advisor — context-aware day planning
  • Telegram bridge — 7 chats in real-time
  • Linear integration — ambient task tracking
Key message: the command center. Everything converges here — calendar, tasks, chats, AI advisor. Built iteratively in Claude Code. Show: VOX query, task panel, Telegram bridge.

4Pipelines

  • Content: 5 skills chained (idea → visual → format → UTM → publish)
  • Lab sprint: full lifecycle from setup to closing week
  • Meeting: Krisp → summary → Telegram → Linear (auto)
  • Presentation: brief → deck → style → dashboard → present
Key message: skills chain into assembly lines. Each pipeline covers end-to-end. Yesterday's dashboard + presentation demo was one pipeline run.

5What the Team Gets

  • 17 shared skills editable in Obsidian
  • 8 MCP server connections (Linear, Notion, TG, Calendar, Krisp, Sheets, Exa, Playwright)
  • Pulse bot: ambient awareness every 2h
  • Claude bot: direct AI access via Telegram
Key message: not a personal toolbox. 17 skills are shared, bots serve everyone, every new skill auto-propagates via Obsidian Sync. The system grows with the team.

6Q&A Preparation

  • “How do team members edit skills?” — Obsidian, Markdown, zero coding
  • “Can the bot access everything?” — allowlist + restricted channels
  • “Security?” — local-only dashboard, no public endpoints, access.json
  • “Can others run Claude Code?” — Dan can, others via bot or Obsidian edits
